文档日期：2026-09-10
当前阶段：产品与技术设计完成，准备进入阶段 0——POC 风险验证
重要说明：本项目将在核心功能、测试和实测评估完成后才写入简历。本文当前用于理解项目、记录决策和准备后续复盘，不把尚未实现的设计描述成已经完成的能力。


一、一句话介绍项目

Sales Research Agent 是一个面向售前工程师的证据驱动型公网调研 Agent。它用于在陌生客户首次交流前，根据客户名称、会议主题和已知背景开展公网研究，生成适合会前完整阅读的调研底稿，并要求报告中的所有外部事实都能追溯到可核验的原始证据。

项目把“可信度”设为硬门槛，把“效率”设为第二目标。系统宁可明确披露信息缺口，也不能为了形成一份看似完整的报告而编造事实或使用不能支持结论的引用。


二、为什么要做这个项目

1. 真实工作背景

售前工程师经常在较短时间内收到一个陌生客户、行业或竞品的调研任务。销售一般会提供客户名称、会议主题和部分已知需求，售前工程师需要手动检索官网、新闻、财报、行业报告、政策材料和竞品资料，再把信息整理成会前底稿。

2. 没有这个工具时通常如何工作

（1）销售把客户和会议信息发给售前工程师；
（2）售前工程师在搜索引擎中反复调整关键词；
（3）打开多个网页和 PDF，人工筛选来源；
（4）复制关键段落、数字和结论；
（5）判断材料是否可信、是否过期、是否相互冲突；
（6）整理成客户背景、行业变化、需求假设、竞品情况和会议问题；
（7）再加工成方案或交流材料。

3. 传统方式的主要问题

（1）信息分散，重复搜索和整理耗时；
（2）事实、推断和建议容易混在一起；
（3）报告中的引用可能真实存在，却不能支持对应结论；
（4）来源内容变化后，结论难以回到当时原文核验；
（5）一个网站访问失败可能影响整条调研流程；
（6）不同人、不同时间运行时，产出质量难以稳定评估；
（7）通用 Agent 可以快速生成内容，但缺少稳定的业务状态、质量门禁和恢复机制。

4. 项目要解决的核心问题

本项目不是单纯提高搜索速度，而是把一次性、容易漂移的 Agent 调研过程，改造成一个可追溯、可恢复、可评测的专业工作系统。


三、产品定位和第一版边界

1. 第一核心用户

第一版以售前工程师个人使用为核心。企业客户类型可能很广，因此底层研究能力要能适应不同企业和行业，但第一版不会为每个行业复制一套独立 Agent。

2. 第一主场景

第一版唯一重点验收场景是：陌生客户首次交流前的公网调研。

典型用户故事是：销售临时发来一个陌生客户，第二天要进行首次技术交流。售前工程师输入客户名称、会议主题、已知需求和研究目标，希望在 30 分钟内得到一份可信的会前调研底稿，在会议前完整阅读、检查证据并准备问题。

3. 第一版输出

（1）结构化的完整调研报告，而不是只有几条摘要；
（2）Markdown 文件，便于保存、编辑和版本管理；
（3）HTML 报告，便于直接在浏览器中阅读；
（4）结论、证据、来源、冲突和信息缺口之间有清晰关系；
（5）报告属于内部工作底稿，不直接作为面向客户的最终方案。

4. 第一版不做什么

（1）聊天 Agent；
（2）AIOps；
（3）会议中的实时 Copilot；
（4）企业内部敏感材料接入；
（5）多租户、复杂权限和分布式部署；
（6）直接面向客户交付的最终解决方案；
（7）没有清晰完成标准的“万能调研 Agent”。

5. 为什么先做本地工具

个人本地工具可以用较低成本验证可信调研链路。如果核心价值被证明，后续可以把数据库、文件存储、后台任务和权限体系替换为云端实现，升级成多人共享的内部服务。第一版通过 Repository、Provider Port 和独立状态层预留替换边界，但不提前承担多人平台的复杂度。


四、为什么不直接使用 Codex、通用 Agent 或一个 Skill

Codex、通用 Agent 或调研 Skill 很适合完成一次性任务，也可以快速生成一份不错的调研结果。但本项目要解决的是长期、可重复的专业流程，它们通常不能稳定提供以下能力：

（1）固定且可解释的研究生命周期；
（2）结构化证据和结论模型；
（3）事实级引用门禁；
（4）长任务断点恢复；
（5）局部失败后的有限重试和降级；
（6）不同版本之间可比较的质量指标；
（7）不可变的报告版本和审计记录；
（8）独立于某个客户端的后端服务。

因此，本项目不是为了证明“自己的 Agent 比 Codex 更聪明”，而是为了把通用模型能力放进一个受约束、可验证的执行环境中。

Skill 仍然可以作为使用入口、任务模板或客户端操作说明，但核心研究状态、证据、报告版本和恢复机制应由独立后端管理。


五、为什么先调研两个旧项目，而不是直接编码

项目开始前已有两个相关 Agent 项目：

项目 A：D:\Dev\Projects\pi_search
它是基于 PiAgent 二次开发的深度调研 Agent。

项目 B：D:\Dev\Projects\oncall-agent
它包含基于 LangChain / LangGraph 的 Python Agent 实现。

我们先阅读两个项目的 README、依赖、入口、Agent 生命周期、工具调用、上下文与记忆、状态管理、流式输出、MCP、异常恢复、观测和测试代码，目的是搞清楚“现有系统实际上如何工作”，避免凭印象重写。

1. 从项目 A 中识别出的通用价值

（1）Evidence-first：先形成证据，再允许形成结论；
（2）引用原文定位；
（3）数字和高影响事实保护；
（4）防止“引用存在但不支持结论”；
（5）联网失败后的降级和失败收敛；
（6）引用核验和可信度相关测试语义。

2. 项目 A 中不应该迁移的部分

（1）PiAgent 特有运行循环；
（2）PiAgent 上下文和消息对象；
（3）框架专用生命周期代码；
（4）与原有 UI、插件和工具注册强耦合的代码。

最终原则是：迁移领域能力和工程经验，不把 PiAgent 代码机械翻译成 Python。

3. 从项目 B 中识别出的价值

（1）Python 和 FastAPI 后端基础；
（2）LangGraph 状态图；
（3）SSE 流式事件；
（4）MCP 适配形式；
（5）Web 服务入口和运行链路。

4. 项目 B 的不足

（1）现有业务更偏聊天和 AIOps；
（2）状态模型不足以表达来源、证据、事实和报告版本；
（3）缺少事实级可信门禁；
（4）部分 MCP 数据属于模拟数据；
（5）现有项目结构不适合直接承载新的调研领域。

最终决定是建立独立新项目，不直接在项目 B 的聊天/AIOps 单体中继续堆功能。


六、核心技术选型

1. Python

用于对齐 Python AI 应用后端岗位，也便于使用 LangChain、LangGraph、FastAPI、Pydantic 和主流解析工具。

2. FastAPI

作为 Web API 层，负责接收调研任务、查询任务状态、恢复任务、提供审阅接口和输出 SSE 事件。

3. LangGraph

负责完整研究生命周期，包括条件路由、并行研究、有限循环、失败恢复、检查点和人工确认。

4. LangChain

负责模型调用、结构化输出和局部工具抽象。它不承担整个长任务的顶层状态机。

5. SQLite

第一版面向单用户本地运行，SQLite 能显著降低部署和维护成本。业务数据库与 LangGraph Checkpointer 在职责上分开。数据库访问通过 Repository 接口隔离，为后续迁移 PostgreSQL 或 MySQL 保留边界。

6. 本地 Artifact Store

用于保存网页原件、PDF、解析结果、Markdown 和 HTML 报告。大正文不放进 LangGraph State，也不直接塞进数据库字段。

7. 网页和 PDF 解析

网页正文解析暂以 Trafilatura 为主候选，动态网页按需降级到浏览器渲染。PDF 解析以 MinerU 为重要候选。这两个选择尚未经过本项目 POC 验证，不能提前描述成已经稳定实现。


七、为什么使用 LangGraph，而不是只使用 LangChain

LangChain 更适合完成局部能力，例如调用模型、获得结构化结果、包装搜索工具和执行一次 Chain。

本项目的核心流程包含：

接收 Brief
→ 用户确认
→ 生成调研计划
→ 搜索和来源发现
→ 获取网页/PDF
→ 解析文档
→ 提取 Evidence
→ 生成 Claim
→ 逐条引用核验
→ 必要时有限补研或修订
→ 编译 ReportModel
→ 输出 Markdown/HTML
→ 质量门禁和交付

其中存在并行任务、条件分支、局部失败、循环、预算限制、人工确认和断点恢复，因此更适合使用 LangGraph 作为显式状态机。

项目不会使用一个无限自由的 ReAct tool loop 统治整个流程。顶层路径由确定性 Graph 控制，只在局部搜索、Query Rewrite 等环节保留受限的 Agent 自主性。


八、可信调研的领域模型

核心数据链为：

Source
→ SourceRevision
→ DocumentBlock
→ Evidence
→ Claim
→ ReportVersion

1. Source

来源实体，例如公司官网、监管机构网站或新闻媒体。

2. SourceRevision

某次运行实际获取到的来源版本，记录抓取时间、内容哈希和状态。即使原网页后来发生变化，也能说明当时使用了什么内容。

3. DocumentBlock

网页或 PDF 解析后的段落、页面、表格等可定位内容块。

4. Evidence

能够回到原文的证据片段，包含引用文本、页码、DOM 定位、来源版本等信息。

5. Claim

准备进入报告的事实、推断或建议。不同类型使用不同可信规则。

6. ReportVersion

经过验证后形成的不可变报告版本。补研不会覆盖旧报告，而是生成新版本。

最关键的约束包括：

（1）所有外部 Fact 必须绑定 APPROVED Evidence；
（2）Inference 必须标明是推断，不能伪装成客户已确认事实；
（3）Recommendation 必须追溯到上游 Claim；
（4）引用存在不等于引用支持结论，必须进行语义支持核验；
（5）报告生成器只能读取批准后的 Claim，不能绕过门禁直接根据网页补写新事实；
（6）证据不足时披露信息缺口，不降低事实准入标准。


九、状态、异常恢复和降级设计

1. 三条独立状态轴

execution_status 表示程序运行到哪里；
report_outcome 表示报告最终是完成、部分完成还是需要审阅；
review_status 表示人工审阅进度。

三者分开可以避免把“程序运行完了”误解成“报告已经可信完成”。

2. 异常恢复原则

（1）单个来源失败不导致整个任务失败；
（2）与该来源无关的分支继续运行；
（3）每种重试和修订都有硬上限；
（4）搜索失败可以改写 Query，但不能无限循环；
（5）HTML 解析失败后才按需使用更昂贵的浏览器方式；
（6）进程崩溃后通过持久化 Checkpoint 恢复；
（7）通过稳定幂等键和 NodeOperation 尽量实现 effectively-once；
（8）不宣称第三方外部调用可以做到严格 exactly-once；
（9）达到 30 分钟后停止扩展搜索，优先完成可信结报；
（10）PARTIAL 可以不完整，但不能降低已保留事实的可信标准。

3. SSE 输出原则

SSE 输出经过筛选的业务事件，而不是直接输出未经验证的模型思维过程或报告 token。例如：正在规划、已发现来源、某来源抓取失败、已核验多少 Claim、报告进入质量检查，以及最终 COMPLETED、PARTIAL 或 NEEDS_REVIEW。


十、与 Harness Engineering 的关系

Harness Engineering 可以理解为：不能只依赖模型本身，要通过外围工程约束模型的输入、工具、状态、错误和输出。

本项目对应的关键点包括：

（1）限制 Agent 自由度：顶层使用显式 LangGraph；
（2）控制上下文：Graph State 只保存 ID 和控制字段；
（3）结构化工具结果：来源、证据、结论都有 Schema；
（4）结果必须验证：Claim 进入报告前执行引用核验；
（5）错误可以恢复：Checkpoint、幂等写入和有限重试；
（6）失败必须收敛：局部降级，到达预算后可信结报；
（7）过程可审计：AuditEvent 和 ReportVersion；
（8）建立质量门禁：无证据外部事实不能进入报告；
（9）人工介入有边界：Brief 确认和高影响冲突审阅；
（10）评测驱动优化：使用固定案例、失败夹具和质量指标比较版本。

十三、为什么下一步是 POC，而不是直接全面开发

继续写设计文档已经不能回答以下问题：

（1）搜索 Provider 对中文企业和官方来源的覆盖是否足够；
（2）网页正文解析的真实成功率如何；
（3）动态网页需要多大比例启用浏览器；
（4）MinerU 处理财报、扫描件和表格 PDF 的效果与成本；
（5）引用语义核验能否识别“真引用、假结论”；
（6）SQLite Checkpointer 是否能正确处理失败和恢复；
（7）30 分钟真实墙钟预算是否合理。

因此阶段 0 应做风险验证型 POC，而不是缩小版的完整产品。

POC 最小链路是：

输入售前背景
→ 生成调研计划
→ 公网搜索
→ 抓取少量普通 HTML 网页
→ 提取事实与证据
→ 生成带引用的结论
→ 执行引用核验
→ 输出 Markdown 和 HTML

POC 第一轮只支持一个主场景、一个真实公开企业样例和普通 HTML 网页。PDF/MinerU 可以先保留接口，在后续独立验证。POC 必须至少真实运行一次公网链路，不能全部使用 Mock 宣称成功。

十五、面试时的 60 秒介绍模板

我做的是一个面向售前工程师的证据驱动型公网调研 Agent。售前调研中的事实可能直接用于客户交流，所以我把可信度设为硬门槛，要求所有外部事实都能回到原始证据，并进一步验证引用是否真的支持结论。

项目使用 Python、FastAPI 和 LangGraph。LangGraph 负责调研计划、搜索、解析、证据抽取、Claim 核验、失败恢复和报告生成的完整生命周期，LangChain 负责模型调用和结构化输出。数据层采用 SQLite、独立 Checkpointer 和本地 Artifact Store。

在实现前，我先审计了一个 PiAgent 深度调研项目和一个 LangGraph Agent 项目，迁移前者的证据链、引用核验和失败收敛思想，但没有迁移框架耦合代码。我通过显式状态图、事实级质量门禁、持久化恢复和评测集，把一次性 Agent 行为固化为可追溯、可恢复、可评测的专业工作流。

注意：只有在项目完成后，才能把上面已经实际实现和测试通过的内容作为简历描述。当前阶段不能把设计目标说成实现结果。


十六、常见面试追问和回答思路

1. 为什么不用普通 RAG？

普通 RAG 更适合从固定知识库检索并回答问题。本项目需要动态发现公网来源、抓取网页和 PDF、处理冲突、执行补研、控制预算、断点恢复并生成版本化报告。RAG 可以作为局部能力，但不能替代完整生命周期。

2. 为什么不用一个 ReAct Agent？

自由 ReAct 循环虽然灵活，但核心路径、门禁和恢复位置容易漂移。这个场景中的事实可能对客户表达，因此顶层使用显式 LangGraph，只在局部研究环节保留受限自主性。

3. 如何避免引用编造？

系统不是在报告完成后让模型补 URL，而是先保存来源版本和可定位 Evidence，再生成 Claim。Fact 必须引用 APPROVED Evidence，并通过语义支持核验，报告只能从批准后的 Claim 编译。

4. 为什么使用 SQLite？

第一版是单用户本地 POC，SQLite 可以降低部署成本。业务库、Checkpointer 和 Artifact Store 职责分离，Repository 隔离具体数据库，后续可迁移 PostgreSQL 或 MySQL。

5. 网站访问失败怎么办？

单来源失败只影响相关问题。系统记录失败原因，执行有限重试或解析降级，其他无依赖分支继续。最终允许生成 PARTIAL 报告并披露缺口，但不会降低保留事实的可信标准。

6. 如何评估这个 Agent？

重点评估外部事实证据覆盖率、引用是否真正支持结论、高影响数字准确性、错误引用拦截能力、单来源失败后的任务完成情况、崩溃恢复正确性、双格式报告一致性、真实耗时和调用成本。所有指标都必须说明样本规模、时间、运行环境和计算方式，不能编造提升比例。

7. 这个项目相比调用大模型 API 有什么技术深度？

项目的重点不是单次模型调用，而是领域建模、状态编排、上下文控制、结构化输出、工具适配、长任务执行、Checkpoint、幂等、异常恢复、证据核验、人工审阅、审计事件和 Agent Evals。


十七、简历使用原则

1. 项目完成前不把它作为“已完成项目”写入正式简历。
2. 项目完成后，只描述已经实现并通过测试或实测的数据。
3. 不使用“生产级”“完全杜绝幻觉”“百分之百可信”等无法证明的说法。
4. 性能和质量提升必须带基线、样本规模、运行日期和测试条件。
5. 如果最终只完成本地单用户版本，要如实说明，不包装成多人 SaaS。
6. 设计文档中的候选方案不等于已经实现的技术栈。
7. 面试重点讲清真实问题、关键取舍、失败案例、验证方式和最终结果，而不只是罗列框架名称。
