## 2. 产品定位

### 2.1 一句话定位

面向售前工程师的证据驱动型调研工作台，在客户沟通或方案准备前，通过公网信息完成客户、行业和竞品研究，并将每项关键结论关联到可核验的原始证据。

从后端技术角度，可以定义为：

> 基于 LangGraph 的可验证深度调研 Agent 后端，通过结构化证据链、持久化状态、异常恢复和自动评测，提高公网调研结果的可信度。

### 2.2 第一版核心用户

第一版以售前工程师个人使用为核心。该用户通常：

- 同时支持多个销售和商机；
- 经常临时接到陌生客户、行业或竞品调研任务；
- 没有充足时间逐篇阅读网页和 PDF；
- 既要快速形成判断，又担心事实或引用错误；
- 需要回答“这个结论从哪里来”；
- 最终会亲自判断、修改并决定哪些内容可以对外表达。

销售、售前经理和解决方案架构师可以作为后续次要用户，但第一版不围绕多人协作设计。

### 2.3 典型启动场景

销售发来一个客户名称，第二天要进行首次客户交流。售前工程师希望在有限时间内完成：

- 客户背景和近期业务变化调研；
- 所在行业趋势及外部驱动因素调研；
- 潜在需求与问题假设；
- 竞品及其他替代方案分析；
- 首次交流验证问题；
- 竞品异议与应答准备。

报告是内部工作底稿，不直接作为面向客户的正式材料。因此允许保留假设、冲突、低置信结论和待确认问题。

该场景已确定为第一版唯一的主场景：

> 销售临时发来一个陌生客户，售前工程师需要为第二天的首次客户交流准备一份可信的调研底稿。

客户背景、行业趋势、需求假设和竞品研究是服务于该主场景的研究能力。它们可以作为内部任务类型和后续独立入口，但第一版产品设计、默认 Brief、报告组合和验收流程均以首次客户交流前调研为中心。

在真实任务起点，销售通常会提供部分背景，而不只是客户名称。典型输入包括：

- 客户名称；
- 会议主题或交流目标；
- 已知需求或销售当前判断；
- 可选的参会角色、已有沟通信息、已知竞品和特别关注点。

这些背景用于缩小研究范围和生成 Research Question，但不自动构成公网 Evidence。

报告的主要使用时点是客户交流前。售前工程师会在会前完整阅读、检查证据并准备问题，第一版不以会议中的实时提示、实时问答或会中 Copilot 为核心体验。

## 3. 问题与替代方案

### 3.1 没有本项目时的常规流程

售前工程师通常需要：

1. 使用搜索引擎反复检索；
2. 打开大量网页和 PDF；
3. 将内容复制到 Word、Markdown 或表格；
4. 使用通用大模型进行总结；
5. 人工检查链接、数字和出处；
6. 再整理为客户沟通材料。

### 3.2 可以直接使用的替代方案

- 通用搜索引擎；
- Codex、ChatGPT 或其他具备联网能力的 Agent；
- 为 Codex 编写固定售前调研 Skill；
- 通用深度研究产品；
- 销售情报数据库；
- 企业内部知识库；
- 人工研究或咨询服务。

### 3.3 为什么不只做一个 Skill

Skill 可以低成本固化调研步骤、报告结构、工具选择和写作规范。对于个人、低频、允许人工复核的任务，Skill 很可能已经足够。因此，新项目必须将“通用 Agent + Skill”视为基线，而不能假装替代方案不存在。

独立项目的必要性来自 Skill 难以稳定保证的能力：

- 引用原文是否真实存在；
- 数字、金额和日期是否在转述中被修改；
- 每项关键事实是否绑定有效证据；
- 事实、推断和建议是否被严格区分；
- 网络局部失败后是否可以降级继续；
- 进程中断后是否能够从持久化状态恢复；
- 整个研究过程是否可以复现和审计；
- 不同版本之间是否可以使用固定数据集回归评测；
- 模型、搜索和抓取服务是否可以替换。

项目的核心问题不是“如何让大模型完成一次调研”，而是：

> 如何把不稳定、难复现的 Agent 调研，转化为可以校验、恢复、评测和追溯的研究流程？

## 4. 产品范围

### 4.1 第一版包含

- 公网客户、行业和竞品调研；
- 无需登录即可访问的公开网页和公开 PDF；
- 结构化 Research Brief；
- 研究计划和动态任务拆分；
- 搜索、抓取、证据提取和来源管理；
- `Source–Evidence–Claim–Citation` 证据链；
- 事实、推断、建议和信息缺口的明确区分；
- 结构化内部调研报告；
- 竞品对照与异议应答材料；
- 引用真实性和证据覆盖校验；
- 网络失败降级、任务重试和断点恢复；
- FastAPI 任务接口和结构化 SSE 事件；
- CLI 或极简演示入口；
- “通用 Agent + Skill”基线；
- Agent 评测集和回归指标。

### 4.2 第一版不包含

- 通用聊天；
- AIOps；
- 面向客户直接交付的最终方案；
- 企业内部知识库；
- 企业产品能力和商务承诺的自动生成；
- 复杂前端；
- 多租户、组织、角色和完整权限系统；
- 以 Milvus 为代表的向量数据库；
- 自动生成完整 PPT；
- 大量 MCP 服务；
- 为展示概念而设计的多 Agent 系统。
- 登录后页面、付费墙和验证码绕过；
- 视频、音频及需要专用多媒体理解的来源；
- 会议中的实时转写、实时问答、话术提示和会中 Copilot；
- 将搜索摘要直接作为最终 Evidence；
- 将普通社交媒体帖子作为高影响事实的独立证据；

### 4.3 后续演进

第一版在结构设计上允许后续扩展为完整售前工作包：

- 售前方案初稿；
- 汇报或 PPT 提纲；
- 竞品对照和异议材料；
- 风险清单；
- 待客户确认问题；
- 企业内部知识库；
- 多人共享服务。

这些产物应复用同一套结构化证据和结论，而不是分别重新联网生成。

### 4.4 场景扩展方式

“首次客户交流前调研”是第一版唯一公开的主入口和重点验收场景，不表示研究内核只能支持这一种任务。

公网调研场景通过 Scenario Profile 配置，至少描述：

```text
scenario_id
display_name
required_inputs
default_questions
default_modules
source_preferences
default_budget
completion_criteria
```

不同场景共享 Research Brief、Research Question、文档摄取、`Source–Evidence–Claim`、来源与时效校验、Checkpoint、Research Gap、引用验证和固定报告核心，只改变默认输入、研究问题、条件模块、预算和完成标准。

计划中的场景映射：

- 首次客户交流：客户洞察、行业市场与政策、需求假设、首次交流准备；
- 客户背景调研：客户洞察；
- 行业趋势调研：行业市场与政策；
- 竞品深度调研：竞品与替代方案、竞争定位与异议应答。

第一版产品界面只突出首次客户交流前调研，不提供含义模糊的“万能调研”入口。后续场景需要分别定义完成标准和评测任务后再开放。

完整售前方案、PPT 或其他工作包不作为普通 Scenario Profile 强行塞进调研流程，而是在可信研究结果之后增加独立 Artifact Graph，并复用已验证的 Claim 和 Evidence。

### 4.5 本地数据与隐私边界

第一版将一次调研视为按 `run_id` 组织的自包含本地运行包。默认保存在本地的内容包括 Research Brief、UserContext、网页或 PDF 原始产物、Evidence、Claim、报告、VerificationResult、失败记录和事件轨迹。

规则如下：

- 默认不进行自动云同步；
- 发送给模型、搜索或其他外部工具的数据遵循最小必要原则；
- UserContext 不得未经处理原样进入外部搜索；
- 外部调用需要记录 Provider、用途和实际发送的字段类别；
- 用户可以按 `run_id` 删除整次运行及其原始产物；
- 默认不单独删除支撑现有报告的原始网页、PDF 或快照，否则会破坏完整证据追溯；
- 报告被单独导出后，如果对应本地运行包已经删除，需要视为失去本地重新校验和完整追溯能力；
- 本地运行包默认保留到用户主动删除，第一版暂不设置自动过期策略；
- 后续多人服务需要另行设计身份、权限、加密、审计、备份和数据保留周期。

“本地保存”不表示运行期间完全没有数据离开本机；模型和搜索 Provider 可能接收完成对应步骤所需的输入。系统必须在配置和运行记录中明确这种外发边界。

## 5. 运行宿主与框架边界

### 5.1 核心运行主体

完整调研流程运行在新项目的 Python LangGraph 后端中。FastAPI、CLI 或 Codex Skill 都只是调用入口。

```text
售前工程师
    ├── CLI / 极简 Web
    └── Codex Skill（可选）
             ↓
         FastAPI / CLI
             ↓
    Python LangGraph 调研引擎
             ↓
模型、搜索、抓取、校验、持久化、评测
```

### 5.2 Codex 的角色

Codex 可以通过 Skill：

- 收集调研参数；
- 调用本地 CLI 或 API；
- 展示和解释报告；
- 帮助用户继续加工研究产物。

Codex 不负责保存核心研究状态，也不控制 LangGraph 内部的每个节点。更换客户端后，调研后端仍应独立运行。

### 5.3 PiAgent 项目的角色

项目 A 是领域能力和工程经验的来源，不再作为新项目的运行框架。

计划迁移的通用能力包括：

- 证据和结论建模；
- 引用原文定位；
- 精确、规范化和模糊匹配；
- 数字一致性保护；
- 来源到结论的 lineage；
- 确定性脚注生成；
- 网络失败分类和降级策略；
- 预算管理；
- 快照、事件和恢复经验；
- 不可信网页内容隔离；
- 测试样例和边界情况。

不计划迁移的框架耦合代码包括：

- Pi extension 生命周期；
- Pi 命令注册；
- Pi 会话和消息模型；
- Pi 专用 UI；
- Pi 工具调用协议；
- TypeScript 编排外壳。

## 6. 为什么使用 LangGraph，而不是只使用 LangChain

### 6.1 两者不是互斥关系

目标技术组合是：

> LangGraph 负责顶层状态化编排，LangChain 负责模型、消息、工具、结构化输出和标准 Agent loop 等高层抽象。

当前 LangChain 的 `create_agent` 本身运行在 LangGraph runtime 之上。因此问题不是选择 LangChain 或 LangGraph，而是是否需要直接使用 LangGraph 暴露的低层编排能力。

### 6.2 LangChain 更适合的场景

LangChain 适合：

- 快速创建模型与工具调用循环；
- 单个 Agent 根据当前消息选择工具；
- 相对直接、执行时间较短的任务；
- 主要状态是消息历史的应用；
- 使用中间件实现通用模型、工具和结构化输出行为。

项目内部仍会使用 LangChain，例如：

- 初始化不同模型 Provider；
- 定义工具 Schema；
- 结构化输出；
- 在研究子图内部运行有限的工具调用循环；
- 统一消息和模型调用接口。

### 6.3 本项目为什么需要 LangGraph

本项目不是一次模型调用，也不只是一个 ReAct 循环。一次运行可能持续数十分钟，包含多个并行任务、多轮补充搜索、人工确认、局部失败和最终硬校验。

需要显式表达：

- `Brief → Plan → Research → Evidence → Claim → Report → Verify`；
- 根据证据覆盖率决定继续研究或进入报告阶段；
- 客户、行业和竞品任务的并行分发与汇总；
- Brief 确认时暂停，用户确认后继续；
- 搜索或抓取失败后的分类路由；
- 报告校验失败后的定向修订；
- 进程退出后的断点恢复；
- 每个阶段的独立观测和评测。

这些需求对应 LangGraph Graph API 的核心优势：显式共享状态、条件分支、循环、并行路径、持久化执行、流式事件和 human-in-the-loop。

### 6.4 技术选择结论

第一版采用：

- 顶层：LangGraph Graph API；
- 研究任务：参数化 Research Subgraph；
- 模型和工具集成：LangChain；
- 数据边界：Pydantic；
- 服务接口：FastAPI；
- 流式状态：SSE；
- 状态持久化：开发阶段使用轻量持久化实现，服务化阶段迁移到 PostgreSQL 等生产存储；
- 观测和评测：先建立自有事件及离线评测接口，再评估是否接入 LangSmith。

### 6.5 文档摄取候选方案

网页与 PDF 的获取和解析属于独立的 Document Ingestion 子系统。LangGraph 负责调度、重试和状态路由，摄取服务负责原始内容保存、解析、质量检查和统一文档输出。

当前确认的候选组合：

- PDF 主解析：MinerU；
- PDF 原生文本定位、交叉检查及降级：PyMuPDF；
- 静态网页获取：HTTPX；
- 网页正文和元数据抽取：Trafilatura；
- JavaScript 动态网页降级：Playwright；
- 统一输出：`NormalizedDocument + DocumentBlock`。

推荐流程：

```text
URL
→ 安全获取并保存 RawArtifact 与内容哈希
→ 根据媒体类型路由到 HTML 或 PDF 解析器
→ 生成带稳定 block_id 和定位信息的 NormalizedDocument
→ 执行解析质量检查
→ 通过后交给 Evidence 提取节点
```

PDF Evidence 需要尽量保存文件哈希、页码、文本块、bbox、解析器版本和 `native_text | ocr | table | image_description` 提取方式。网页 Evidence 需要保存最终 URL、HTML 快照哈希、标题层级、文本块和必要的 DOM 定位信息。

动态渲染、OCR 和复杂表格解析都属于按需降级路径，不能成为所有来源的默认高成本流程。登录、付费墙和验证码不做绕过；解析质量不足的文档只能作为线索、进入人工复核或记录失败。

MinerU 的具体 Backend、本地 CLI 或独立服务运行方式、模型缓存和硬件成本暂不锁定。后续使用真实财报、政策文件、白皮书和扫描 PDF 进行对照测试后再确定。

## 7. Agent 组织方式

第一版不刻意采用多个拥有独立人格、记忆和工具集的 Agent。

采用：

> 一个顶层 LangGraph、一个可复用研究子图、若干确定性领域服务。

```text
Research Graph
├── Brief Node
├── Planner Node
├── Task Dispatcher
├── Research Subgraph × N
│   ├── Query Generator
│   ├── Search
│   ├── Source Selection
│   ├── Fetch
│   ├── Evidence Extraction
│   └── Task Claim Synthesis
├── Evidence Aggregator
├── Coverage / Gap Analyzer
├── Report Composer
├── Deterministic Verifier
├── Semantic Verifier
└── Finalizer
```

客户、行业和竞品研究共享同一个生命周期，因此通过参数化子图并行运行。只有当某一角色拥有明显不同的工具、权限、长期状态或独立优化目标时，才考虑升级为独立 Agent。

## 8. Research Brief 与核心生命周期

### 8.1 Research Brief 输入契约

用户使用自然语言发起任务，第一版只要求三个最小必填项：

- **调研对象**：企业、产品、行业或竞争对手；
- **使用场景**：首次客户交流、客户背景调研、行业研究、竞品分析或综合售前调研；
- **重点关注**：用户希望优先回答的问题。

Agent 将自然语言转换为结构化 Research Brief，并自动提出以下字段的默认值：

```text
subject.name / type / official_domain / aliases / resolution_status
scenario
objective
research_questions
scope.time_range / regions / languages / source_types
competitors
user_context
exclusions
output
budget
```

关键规则：

- 对同名企业、集团与子公司、企业与产品等歧义进行对象消歧；
- 对象消歧可以执行少量预检搜索，但用户确认前不得启动完整调研；
- 每个 Research Question 需要具有稳定 ID、优先级和完成标准，后续 Research Task 必须能够追溯到具体问题；
- 用户提供的背景信息保存为 `user_context`，默认标记为 `unverified`，不能自动转为外部事实；
- `user_context` 需要保存信息来源类型，并与公网 Source 分开展示；已知需求可以指导搜索和推断，但在没有外部证据或客户现场确认时不能写成公开事实；
- 用户背景可以参与研究规划，但默认不能作为 Evidence；可能包含敏感信息的内容不得原样拼入外部搜索词，也不得发送给完成当前步骤不需要的第三方工具；
- 用户可以指定竞品，系统仍需考虑自建、维持现状、人工流程和不采购等替代方案；
- 可信度和证据规则不能由用户关闭；
- 预算表示最大运行时间、搜索次数、有效来源数量和补充研究轮数等执行上限，不要求必须耗尽；
- 系统向用户展示对象、范围、重点问题、默认值和预算摘要，用户确认后冻结 Brief 并开始正式研究；
- 用户修改 Brief 后需要产生新版本，已经冻结的版本不得被静默覆盖。

### 8.2 主流程

1. 创建研究运行并生成 `run_id`；
2. 将自然语言需求转换为 Research Brief；
3. 暂停并等待用户确认调研范围；
4. 生成研究计划和任务依赖图；
5. 并行执行客户、行业和竞品研究任务；
6. 搜索候选来源并完成 URL 规范化、去重和筛选；
7. 抓取网页并保存来源内容哈希或快照；
8. 从来源中提取能够回到原文位置的 Evidence；
9. 基于 Evidence 形成事实、推断和建议类型的 Claim；
10. 检查研究问题覆盖、来源冲突和信息缺口；
11. 信息不足且预算允许时，生成补充研究任务；
12. 预算耗尽或公网无法确认时，写入 Research Gap；
13. 报告节点只使用已经批准的 Claim 和 Evidence 编译报告；
14. 执行确定性引用校验和语义支持度校验；
15. 对可修复问题进行定向修订，对无证据内容删除或降级；
16. 固化报告、验证结果、失败记录和完整事件轨迹。

### 8.3 人工介入点

第一版保留两个用户介入点：

- 调研 Brief 确认；
- 最终报告审阅。

中间的搜索、补充研究、失败降级和引用修复自动执行。

### 8.4 失败原则

- 临时网络错误：有限重试；
- 搜索服务不可用：切换适配器或降级；
- 单个网页失败：记录失败并继续处理其他来源；
- 引用无法定位：拒绝该 Evidence；
- 证据不足：补充研究或记录 Gap；
- 进程中断：从 Checkpoint 恢复；
- 预算耗尽：输出明确标注限制的部分报告。

局部失败不应默认导致整个任务失败，但任何失败都必须被记录，不能静默忽略。

面向用户的异常恢复规则：

- 搜索、抓取、PDF 解析或模型调用发生局部失败时，系统先进行有限自动重试，再尝试已配置的 Provider、解析器或执行路径降级；
- 一个来源或研究任务失败时，其他不依赖它的研究分支继续运行；Failure 必须绑定受影响的任务、Source 和 Research Question；
- 运行详情向用户说明发生了什么、影响哪些研究问题、是否正在恢复，以及可能如何影响报告；原始异常栈和技术元数据默认折叠；
- 自动恢复结束后，用户可以重试具体失败项、跳过该来源，或者提前停止扩展研究并生成可信 `PARTIAL`；
- 非关键来源失败但研究覆盖和可信门槛仍满足时，运行可以进入 `COMPLETED`，相关 Failure 仍保留在审计记录中；
- 必需问题未完全覆盖，但已经获得的内容全部可信且仍有使用价值时进入 `PARTIAL`；存在需要人工裁决的高影响证据冲突时进入 `NEEDS_REVIEW`；无法形成任何可信可用报告时才进入 `FAILED`。

### 8.5 运行终态

研究运行具有四种最终状态：

- `COMPLETED`：报告中的全部外部事实均通过引用真实性、语义支持度、来源等级和时效性校验；允许存在已经明确展示的 Research Gap；
- `PARTIAL`：部分必要研究问题因公网无资料、预算耗尽或工具失败而未完成，但报告中已经保留的事实全部通过可信度硬门槛；
- `NEEDS_REVIEW`：存在来源冲突、语义支持度难以自动判断，或高影响事实只能获得不满足接纳规则的来源，需要人工裁决；
- `FAILED`：核心调研无法产生足够证据、关键系统错误导致流程无法继续，或者运行状态无法安全恢复。

`PARTIAL` 表示“不完整但可信”，不能包含未经验证的事实。Research Gap 本身不阻止 `COMPLETED`；未披露的关键缺口、未经验证的外部事实或未处理的高影响冲突才会阻止运行进入 `COMPLETED`。

### 8.6 研究覆盖与停止策略

Agent 按 Research Question 的覆盖情况决定是否继续研究，不由模型使用模糊的“资料已经足够”自由终止，也不使用每个问题固定搜索次数作为唯一停止条件。

每个 Research Question 至少保存：

```text
question_id
priority
required_outputs
preferred_source_tiers
completion_criteria
status
unresolved_gaps
```

问题状态包括：

- `answered`：已经形成满足证据规则和完成标准的结论；
- `partially_answered`：只有部分子问题获得可靠证据；
- `unanswered`：未获得足够证据；
- `blocked`：因来源不可访问、可靠来源冲突或其他明确限制无法继续。

继续搜索需要同时满足：

1. 存在尚未完成的高优先级问题；
2. 系统仍能生成与已有查询或来源有实质差异的研究动作；
3. 尚未达到时间、搜索次数、补充轮数和成本预算。

满足以下任一条件时停止扩展搜索：

- 所有高优先级问题均达到完成标准；
- 剩余问题继续搜索的预期信息增益已经很低；
- 继续搜索只会产生重复查询、同稿转载或相同来源；
- 预算已经耗尽；
- 关键外部限制使问题进入 `blocked`。

停止搜索不代表所有问题都已回答。所有 `partially_answered`、`unanswered` 和 `blocked` 问题必须进入 Research Gap 或冲突部分，并参与最终运行状态判断。

第一版主场景采用 30 分钟时间盒。达到时间盒后：

1. 停止创建新的搜索和补充研究任务；
2. 允许已经接近完成且不会明显超出收尾预算的节点安全结束；
3. 对当前 Evidence 和 Claim 完成必要的可信度校验；
4. 能形成可信结果时优先输出明确标注缺口的 `PARTIAL` 报告；
5. 无法形成可信结果时进入 `NEEDS_REVIEW` 或 `FAILED`，不能拼凑报告；
6. 用户审阅后可以针对具体 Research Gap 主动发起后续研究。

后续研究属于原运行的显式续跑，需要保留新的预算、触发者、触发时间和所针对的 Gap；系统不在时间盒结束后默认无限后台运行。

## 9. 核心状态模型

计划中的顶层状态至少包含：

```python
class ResearchState(TypedDict):
    run_id: str
    status: str
    review_status: str
    brief: ResearchBrief
    plan: ResearchPlan
    tasks: list[ResearchTask]
    sources: list[Source]
    evidence: list[Evidence]
    claims: list[Claim]
    gaps: list[ResearchGap]
    conflicts: list[Conflict]
    failures: list[Failure]
    budget: ResearchBudget
    report: ResearchReport | None
    verification: VerificationResult | None
```

`status` 与 `review_status` 是两个正交维度：

- `status` 表示系统运行终态：`COMPLETED | PARTIAL | NEEDS_REVIEW | FAILED`；
- `review_status` 表示用户审阅进度：`UNREVIEWED | IN_REVIEW | REVIEWED`；
- `NEEDS_REVIEW` 表示系统遇到无法自动消解的冲突、证据不足或可信度问题，不等同于用户尚未阅读报告；
- 只有全部高影响 Claim 均被用户“接受”或“驳回”后，报告版本才能进入 `REVIEWED`；低影响 Claim 不作为完成审阅的强制条件。

重要原则：

- 系统保存可计算的研究状态，而不只是聊天消息；
- 网页原文、Evidence、Claim 和报告上下文分层保存；
- 报告生成器不能直接访问未处理的网页内容；
- ID 必须稳定，保证 Source、Evidence、Claim 和 Citation 可以追踪；
- 节点需要考虑幂等性，防止恢复时重复调用外部 API 或重复写入数据。

## 10. 结构化报告

### 10.1 报告目的

第一版输出的是售前工程师内部研究底稿。报告帮助用户判断：

- 这个客户或机会是否值得继续研究；
- 哪些发现最重要；
- 哪些只是推断；
- 下一次沟通应该验证什么；
- 哪些竞品或替代方案需要准备；
- 哪些结论当前没有足够证据。

报告首先是一份适合会前连续阅读和审阅的内部文档，而不是实时会议仪表盘。交互能力用于展开证据、处理冲突、批注和触发补充研究，不需要为了会中速查把正文压缩成碎片化卡片。

第一版报告载体：

- 结构化 `ResearchReport` 是唯一内容真源；
- 浏览器 HTML 是主要阅读和审阅界面，支持展开 Evidence、查看原始 Source、识别运行状态和触发结构化审阅动作；
- Markdown 是正式导出格式，保留章节、Claim 类型、状态、脚注、来源和信息缺口，便于用户继续编辑或归档；
- 第一版采用“HTML 结构化审阅、Markdown 自由编辑”的职责边界：HTML 提供证据展开、来源跳转、状态标记、批注和补充调研等受控动作，不建设类似 Word 的全文富文本排版编辑器；
- 用户如需大幅改写报告，导出 Markdown 后编辑；若未来在 HTML 中支持事实内容修改，必须同时设计 Claim 失效、重新核验和版本追踪机制；
- HTML 和 Markdown 必须由同一版本的 ResearchReport 渲染，不能由模型分别生成两份可能不一致的报告；
- 导出文件必须保留运行状态、`as_of_date`、报告版本和证据引用；
- Word 和 PDF 导出不是第一版必需能力，后续根据实际共享需求增加。

第一版浏览器产品由四个核心视图构成：

1. **新建调研**：填写并确认 Research Brief；
2. **运行详情**：查看当前阶段、研究问题覆盖、耗时、失败与降级情况，并支持取消运行或提前停止并生成可信 `PARTIAL`；
3. **报告审阅**：完整阅读报告、查看证据和来源、审阅 Claim、添加批注、发起局部补充调研并导出 Markdown；
4. **历史记录**：按 `run_id` 查看历史调研、报告版本、运行终态和人工审阅状态。

这四个视图构成第一版最小浏览器闭环。第一版不增加独立仪表盘、复杂统计后台、多人协作、账号权限或模板商城。

第一版浏览器端的最小审阅闭环包括：

1. 展开 Claim 的 Evidence，并打开对应原始 Source；
2. 将 Claim 标记为“接受”“待核实”或“驳回”；
3. 为 Claim 添加个人批注；
4. 针对某条 Claim 或信息缺口发起补充调研；
5. 导出当前报告版本的 Markdown。

所有审阅动作必须绑定 `run_id`、报告版本和具体 `claim_id`（针对问题缺口时绑定 `research_question_id`）。第一版不允许用户直接修改 Source、Evidence 摘录或报告中的事实正文，防止绕过证据校验并造成引用关系失效。

补充调研采用同一 `run_id` 下的局部增量研究机制：

- 用户从某条 Claim 或信息缺口发起补充调研，并可以附加补充说明；
- 系统只重新检索该目标及其依赖范围，不默认重跑完整调研流程；
- 新获得的 Evidence 进入该运行的统一证据池，不覆盖或静默替换旧证据；
- 系统重新校验受影响的事实 Claim，以及依赖这些事实的推断和建议；
- 补充调研生成新的不可变报告版本（如 `v2`、`v3`），旧版本及其审阅记录继续保留；
- 新旧版本应能比较 Claim、Evidence、状态和正文结论的变化；
- 未受影响的章节复用上一版本结果，以控制时延、模型调用量和公网检索成本。

人工审阅状态按 Claim 的实质变化情况继承：

- Claim 内容、所依赖 Evidence 及支持状态均未变化时，可以继承上一报告版本的审阅状态，但必须标注继承来源版本；
- Claim 内容、关键 Evidence 或支持状态任一发生变化时，上一版本的“接受”状态自动失效，新版本恢复为“待核实”；
- 上一版本被“驳回”的 Claim 经补充调研后发生实质变化时，也必须重新审阅，不能自动沿用驳回状态；
- 批注和审阅操作历史始终保留，并绑定其产生时的 `report_version` 和 `claim_id`；
- HTML 版本对比应突出 Claim 的新增、删除、结论变化、Evidence 变化和支持状态变化。

用户驳回 Claim 后采用“正式报告排除、审计历史保留”的规则：

- 被驳回的 Claim 从执行摘要和正式正文中排除；
- 依赖该 Claim 的推断和建议同时失效，并在必要时重新生成或降级；
- 原 Claim、Evidence、驳回原因及操作记录不删除，保留在本地审计历史中；
- 默认 Markdown 不展示被驳回项，后续可提供包含审阅排除项的审计版导出；
- “待核实”Claim 可以保留在报告中，但必须醒目标记，且不能表述为已确认事实。

### 10.2 报告结构

报告采用“必需头部 + 固定核心章节 + 按场景加载的条件模块”。场景可以决定默认加载哪些条件模块，用户可以在 Brief 确认阶段增删模块，但不能关闭必需头部、固定核心、证据规则和风险披露。

#### 10.2.1 必需头部

每份报告必须展示：

- 调研对象与使用场景；
- `COMPLETED`、`PARTIAL`、`NEEDS_REVIEW` 或 `FAILED` 运行状态；
- `as_of_date`、调研时间范围和生成时间；
- `run_id` 和报告版本。

#### 10.2.2 固定核心章节

1. **执行摘要**：3～5 条关键发现、主要售前影响、重要风险和报告可信度状态；
2. **研究范围与问题覆盖**：研究目标、范围、排除项、核心问题，以及每个问题的已回答、部分回答或无法回答状态；
3. **关键发现与售前含义**：跨模块汇总重要 Claim，区分事实、推断和建议，并展示影响等级、证据、有效时间和限制；
4. **风险、冲突与信息缺口**：展示来源冲突、低等级来源、过期信息、抓取失败、未确认需求和公网无法回答的问题；
5. **待验证问题与下一步动作**：列出售前应向客户、销售或内部团队确认的问题，以及后续调研动作和暂不适合对外表达的判断；
6. **证据账本与来源**：提供 `Claim → Evidence → Source` 的完整追溯入口，包括原文、位置、来源等级、发布时间、访问时间、时效状态和校验状态。

执行摘要必须控制在一页以内，并固定包含以下字段：

1. **调研结论**：一句话表达当前最重要的整体判断；
2. **关键发现**：3～5 条，每条展示支持状态并引用对应 `claim_id`；
3. **售前影响**：说明这些发现对首次客户交流意味着什么；
4. **主要风险与信息缺口**：指出哪些信息不能作为确定事实；
5. **优先验证问题**：列出会议中最需要确认的 3～5 个问题；
6. **可信状态**：展示运行终态、人工审阅状态、`as_of_date` 和研究问题覆盖情况。

执行摘要只能压缩和组织详细报告中已经存在且完成相应校验的 Claim，不得在摘要生成阶段引入新的外部事实、推断或建议。摘要中的每项判断都必须能够跳转到正文 Claim 及其证据链。

固定章节不得为了形式完整而生成空话。没有相关结果时，应明确展示“未发现”“无法回答”或“本次未识别到高影响冲突”等状态。

报告采用分层阅读体验：

1. **第一层：决策摘要**——报告状态、一页以内的执行摘要和最重要风险；
2. **第二层：行动准备**——3～7 条关键发现、需求假设、待验证问题和下一步动作；
3. **第三层：分析细节**——按场景加载的客户、行业、竞品等条件模块；
4. **第四层：证据审计**——Evidence、Source、冲突、失败及必要运行记录。

整份报告不设置固定字数。执行摘要的一页限制属于信息密度目标，不得通过省略风险、删除必要引用或降低证据要求实现。条件模块缺少有效信息时不生成空泛段落；Evidence 和技术运行细节在交互界面中可以默认折叠，但必须随时可展开核验。

可点击 HTML 原型中的报告内容仅用于验证信息层级和交互，不作为正式报告篇幅样板。真实报告的深度由 Research Brief、研究问题覆盖、有效证据数量、冲突与条件模块共同决定：需要充分展开已经得到证据支持的分析，同时拒绝为了增加页数而生成重复内容或无证据填充。报告完整性以问题覆盖和证据质量衡量，不以字数或页数衡量。

#### 10.2.3 条件模块

- **A 客户洞察**：企业与业务概况、经营和战略变化、组织信息、重大事件、公开项目、采购及技术建设线索；
- **B 行业、市场与政策**：行业驱动因素、技术趋势、政策监管、市场数据和同类企业实践；
- **C 需求假设**：公开信号、需求假设、证据、置信状态、潜在影响、验证方式和假设不成立时的影响；
- **D 竞品与替代方案**：直接竞品、自建、延续现有方案、人工流程和不采购等替代方案的能力、适用场景、优势、限制与证据；
- **E 竞争定位与异议应答**：可强调和应避免的比较角度、潜在异议、回应逻辑、追问问题及不能作出的承诺；
- **F 首次交流准备**：优先验证问题、提问依据、期望确认信息和不同回答对应的后续方向。

“竞品与替代方案”和“竞争定位与异议应答”采用统一的卡片契约，每张卡片至少包含：

```text
alternative_id          稳定标识
name                    替代对象名称
alternative_type        competitor / build / existing_system / manual / no_purchase
customer_scenario       对应的客户场景与问题
comparison_dimensions   与当前场景相关且有证据支持的比较维度
strengths               优势及其适用条件
limitations             限制及其适用条件
customer_relevance      为什么与当前客户或会议目标相关
likely_objection        客户可能提出的异议
response_logic          建议回应逻辑
follow_up_questions     应继续向客户确认的问题
forbidden_commitments   不应作出的承诺或无证据断言
claim_ids               所依赖的事实、推断和建议 Claim
evidence_ids            所依赖的 Evidence
research_gaps           信息缺口与待验证项
```

卡片不能把产品能力列表直接当作客户价值，也不能默认本方方案优于替代方案。优势、限制和比较维度中的外部事实均遵守统一证据规则；回应逻辑属于建议，必须追溯到上游 Claim，并明确其适用条件。

#### 10.2.4 场景默认映射

| 场景 | 默认加载模块 |
| --- | --- |
| 客户背景调研 | A 客户洞察 |
| 行业趋势调研 | B 行业、市场与政策 |
| 竞品分析 | D 竞品与替代方案、E 竞争定位与异议应答 |
| 首次客户交流 | A 客户洞察、B 行业市场与政策、C 需求假设、F 首次交流准备 |
| 综合售前调研 | A、B、C、D；用户明确需要时加载 E、F |

#### 10.2.5 发现卡片

报告中的关键发现使用统一结构，不向用户展示由模型随意生成的 0～100 置信度分数。每个发现至少包含：

```text
claim_id              稳定的结论标识
statement             具体陈述
claim_type            fact / inference / recommendation
impact_level          high / normal
support_status        verified / corroborated / disputed / insufficient
source_tier           tier_1 / tier_2 / tier_3
validity_status       current / historical / stale / unknown
validity_period       结论适用或观察时间范围
evidence_ids          关联证据
evidence_summary      对支持与反对证据的简要说明
business_implication  对售前任务的含义
limitations           限制条件
```

发现卡片的用户界面必须展示：`claim_id` 与结论、Claim 类型、影响等级、支持状态、时效状态、证据数量与最高来源等级、售前含义，以及限制、冲突或信息缺口。卡片提供展开证据、人工审阅和补充调研操作。默认阅读态突出结论与售前含义，Evidence 原文、Source 定位和技术元数据折叠展示，但不得隐藏其存在性和支持状态。

`support_status` 的含义：

- `verified`：存在满足接纳要求的一级来源；
- `corroborated`：没有一级来源，但存在两个相互独立且语义一致的二级来源；
- `disputed`：可靠来源之间存在尚未解决的冲突；
- `insufficient`：证据不足，只能作为待验证线索或信息缺口。

上述状态描述证据支持情况，不表示客观事实为真的数学概率。`disputed` 和 `insufficient` 的外部事实不得以确定语气进入 `COMPLETED` 报告正文，只能出现在冲突、限制或待验证部分。

#### 10.2.6 事实、推断与建议的双层 Lineage

系统维护两类追溯关系：

```text
外部事实 Claim → Evidence → Source
推断 Claim     → premise_claim_ids
建议 Claim     → inference_ids / fact_claim_ids
```

推断不能凭空生成，至少需要保存：

- 作为前提的事实 Claim；
- 从前提到结论的推理依据；
- 已发现的反面信息；
- 适用范围和限制条件；
- 可以确认或证伪该推断的客户问题。

建议必须关联支持它的事实或推断，并说明与当前 Research Brief 目标的关系。无法建立上游 Claim 关系的建议不得进入最终报告，只能作为待人工补充的草稿内容。

例如：

```text
事实 F1：客户正在整合多个业务系统
事实 F2：客户公开提出统一数据标准
        ↓
推断 I1：客户可能存在数据治理需求
        ↓
建议 R1：首次交流优先确认数据标准和责任归属
```

双层 Lineage 使用户不仅能检查事实来自哪里，也能检查系统为什么得到某项售前判断和建议。

每项重要发现应尽量包含：

> 结论 + 结论类型 + 业务影响 + 证据 + 置信度 + 反面信息 + 限制 + 待验证问题 + 建议动作

### 10.3 报告生成约束

- 报告生成器不得临时联网补充事实；
- 所有外部可验证的事实陈述都必须绑定至少一条通过校验的 Evidence，而不只要求核心结论有证据；
- 外部事实包括但不限于企业信息、人物与组织关系、日期、数字、金额、比例、产品能力、事件、政策、市场数据和竞品信息；
- 无法绑定有效 Evidence 的外部事实不得进入最终报告，只能删除、降级为明确标识的待验证假设，或写入 Research Gap；
- 连续事实可以在展示层共用脚注，但内部必须保留每个事实 Claim 到 Evidence 的精确映射，不能只做段落级模糊引用；
- 计算或归纳得到的派生事实必须保存输入 Evidence、计算方法和适用范围；
- 推断必须明确标识，不得写成客户已确认需求；
- 推断必须关联前提事实 Claim，建议必须关联事实或推断 Claim；无法建立上游关系的推断和建议不得进入最终报告；
- 没有内部产品资料时，不得声称本方产品支持具体能力；
- 竞品分析必须包含自建、维持现状和不采购等替代方案；
- 信息不足时输出 Gap，不得为了报告完整而编造内容。

### 10.4 来源分级与接纳规则

所有引用需要同时通过三类检查：

1. **引用真实性**：引用文本或对应信息能够在保存的来源内容中定位；
2. **语义支持度**：来源内容能够支持 Claim 的实际含义，而不只是出现相似关键词；
3. **来源可信度**：来源级别与该事实的重要程度匹配。

来源分为三级：

- **一级来源**：企业公告、财报、政府和监管机构、标准组织、论文、产品官方文档等原始或权威材料；
- **二级来源**：可信新闻媒体、行业研究机构、专业分析报告等具有编辑或研究责任的材料；
- **三级来源**：普通博客、论坛、内容聚合、营销软文和转载网站等，仅用于发现线索或补充背景。

接纳规则：

- 高影响事实优先由一级来源支持；
- 找不到一级来源时，高影响事实至少需要两个相互独立的二级来源交叉支持；
- 三级来源原则上不能单独支撑高影响事实；
- 同一原始稿件的转载、引用同一未公开信源的报道，不能视为相互独立的来源；
- 来源级别不能只根据域名静态决定，还需要结合具体页面类型、作者、发布时间和原始出处判断；
- 来源冲突时不得自动选择对当前结论更有利的一方，应保存 Conflict 并在报告中展示；
- 无法满足来源要求的内容只能降级为待验证线索或 Research Gap。

Claim 增加 `impact_level: high | normal` 字段。以下内容默认视为高影响事实：

- 客户经营、财务和组织信息；
- 客户战略、在建项目、采购及技术栈；
- 市场规模、市场份额和增长率；
- 法律、政策、监管与合规要求；
- 竞品功能、性能、价格和客户案例；
- 用于判断客户需求或竞争切入点的关键事实；
- 可能在客户交流中被直接引用的数字和判断依据。

高影响等级由确定性规则与模型分类共同产生。模型可以建议等级，但不得绕过来源接纳规则；当分类存在不确定性时，默认采用更严格的 `high` 等级。用户或最终审阅者可以将普通事实提升为高影响事实，但降低等级需要记录理由。

### 10.5 信息时效规则

每份报告必须保存并展示统一的 `as_of_date`。Source、Evidence 和 Claim 均需要保存适用的发布时间、事件时间、访问时间和时效状态，避免将历史事实误写为当前状态。

默认时效规则：

- 当前经营状态、组织信息和竞品能力：优先使用最近 12 个月的材料；
- 市场规模、市场份额和增长率：优先使用最近 24 个月的材料，并注明实际统计周期；
- 法律、政策、监管和合规要求：必须核对当前有效的官方版本及生效状态；
- 历史事件：允许使用更早来源，但必须明确事件发生时间，不能用现在时表达历史状态；
- 无发布时间的网页：降低可信度，不能单独支撑高影响的时效性事实；
- 只能找到超过默认时间窗口的来源时，可以保留相关信息，但必须标记为 `stale` 并进入待验证项；
- 用户可以在 Research Brief 中覆盖默认时间范围，但系统必须记录覆盖理由和最终采用的时间边界。

建议为 Claim 保存 `validity_status: current | historical | stale | unknown`。时效校验失败不能静默忽略；对高影响事实，`stale` 或 `unknown` 默认阻止其作为确定的当前事实进入最终报告。

### 10.6 用户审阅、修改与版本

售前工程师可以：

- 接受或驳回某个 Claim；
- 将 Claim 标记为需要人工复核；
- 查看关联 Evidence 和原始 Source；
- 针对某个 Research Gap 请求补充研究；
- 添加与具体 Claim 或问题绑定的个人批注；
- 导出当前报告版本的 Markdown。

第一版 HTML 不允许直接修改报告正文、Source 或 Evidence。用户可以在导出的 Markdown 中自由编辑，但导出后的外部改动不属于系统内已验证的报告版本，也不能自动保留原验证状态。

修改规则：

```text
只修改表达方式 → 判断语义是否改变；未改变时可以保留事实 Lineage
修改事实含义   → 原验证结果失效，必须重新绑定 Evidence 并校验
增加外部事实   → 必须先创建 Claim、绑定 Evidence 并通过校验
删除事实       → 允许，但保留版本和审计记录
```

每份报告和 Claim 需要保存版本、生成来源、修改者、修改时间及其对应的 VerificationResult。验证状态只对被校验的具体内容版本有效，不能在内容发生实质变化后自动继承。

未完成全部高影响 Claim 审阅时仍允许导出，但 HTML 和 Markdown 均必须醒目标明 `UNREVIEWED` 或 `IN_REVIEW`，不能展示为最终人工审阅版。

用户审阅不会把 UserContext 自动变成公网事实。用户确认某项客户现场信息时，应记录为独立的用户确认来源类型；它可以用于内部判断，但不能伪装成公开 Source。

### 10.7 异常终态的查看与导出

- `COMPLETED`：允许正常审阅、接受和导出；
- `PARTIAL`：允许查看和导出，但报告头部必须醒目标明未完成状态，并列出未回答问题；用户可以针对具体 Research Gap 发起补充研究；
- `NEEDS_REVIEW`：允许查看 Evidence、Source 和冲突信息并进行人工裁决，但不能标记或导出为“已验证完成”；人工处理后必须重新执行相关校验；
- `FAILED`：展示失败阶段、分类、原因和已经安全保存的产物，允许从有效 Checkpoint 重试，但不能生成或导出伪完整报告。

`PARTIAL` 和 `NEEDS_REVIEW` 可以为了内部紧急使用而导出，但运行状态、风险标识和相关 Claim 状态必须保留。任何导出渠道都不得通过移除状态标识将异常终态伪装成 `COMPLETED`。

## 11. 领域 Agent Harness 设计

本项目将 LangGraph 作为运行时，并在其上建设面向调研领域的 Agent Harness。

计划覆盖的 Harness Engineering 要点包括：

1. **Agent 可读性**：将 Brief、Plan、Task、Source、Evidence、Claim 等研究过程显式化；
2. **强制不变量**：通过 Schema、校验器和状态路由保证关键事实必须具有有效证据；
3. **工具契约**：工具输入、输出和错误均使用类型化结构；
4. **上下文工程**：网页原文、证据片段、结论和报告上下文分层，控制上下文规模；
5. **持久化执行**：使用 Checkpoint 和稳定产物跨节点及进程恢复；
6. **有界自主性**：限制搜索次数、来源数量、重试次数、补充轮数、成本和时长；
7. **Human-in-the-loop**：在 Brief 和最终报告阶段引入人工判断；
8. **不可信输入隔离**：网页内容只作为数据，防止提示注入、SSRF 和越权工具调用；
9. **观测与调试**：记录节点、任务、工具、证据、失败、耗时、Token 和状态变化；
10. **评测反馈循环**：区分模型、Prompt、上下文、工具、编排、校验器和外部服务故障。

项目暂不需要支持任意代码执行，因此不会为了展示 Harness 概念引入通用代码沙箱。是否需要更强的沙箱能力，应由未来工具权限决定。

## 12. 评测策略

### 12.1 基线

使用相同调研题目对比：

- 通用 Agent 直接执行；
- 通用 Agent + 售前调研 Skill；
- LangGraph 调研引擎；
- LangGraph 调研引擎 + Skill 入口。

### 12.2 主要指标

- 引用有效率；
- 关键结论证据覆盖率；
- 引用与结论的语义支持度；
- 事实、推断和建议分类准确性；
- 报告结构完整率；
- 任务完成率；
- 故障注入后的恢复成功率；
- 重复运行的一致性；
- 运行时延；
- Token 和工具调用成本。

所有简历量化指标必须来自固定评测集的真实结果，不预先编造提升比例。

### 12.3 成功目标优先级

已确认第一版采用以下优先级：

1. **P0 可信度硬门槛**：未满足可信度要求的运行不得标记为成功完成；
2. **P1 报告可用性**：在可信的前提下，报告应覆盖售前进行首次交流准备所需的核心信息；
3. **P2 运行效率**：在前两项成立后，再优化总时长、Token、搜索次数和人工核验时间。

可信度硬门槛的候选定义如下，具体阈值仍需通过基线任务校准：

- 报告中不存在无法解析或指向错误来源的引用；
- 所有事实类型的 Claim 必须绑定通过校验的 Evidence；
- 引文必须能够在保存的来源内容中定位，数字、金额和日期不得被静默改写；
- 推断和建议必须明确标识，不得伪装成客户已经确认的事实；
- 来源冲突、抓取失败和信息缺口不得静默隐藏；
- 未通过硬门槛时，运行只能进入 `NEEDS_REVIEW`、`PARTIAL` 或 `FAILED`，不能进入 `COMPLETED`。

效率指标不能通过减少必要校验、隐藏失败或放宽证据要求来改善。第一版允许报告不完整，但不允许以确定语气补全没有证据的内容。

运行状态也是成功标准的一部分。固定评测集需要分别统计 `COMPLETED`、`PARTIAL`、`NEEDS_REVIEW` 和 `FAILED` 的比例，不能将部分完成或待人工裁决统一计算为成功。

### 12.4 可行性与指标口径

成功指标必须区分“系统可以确定性保证的结构不变量”和“只能通过样本估计的模型质量”，不能提出在现实中无法验证或无法达到的承诺。

`COMPLETED` 要求以下系统可控的结构不变量达到 100%：

- 所有引用 ID 都能解析到实际保存的 Source；
- 所有外部事实 Claim 都绑定通过结构校验的 Evidence；
- 所有引用 Evidence 都能在保存的来源内容中完成原文定位；
- 所有高影响事实都满足已经配置的来源分级规则；
- 所有已识别的过期、未知时间和来源冲突均被显式标识；
- 所有已捕获的工具及节点失败均留下事件记录；
- 报告生成器不能绕开 Claim 数据模型临时增加外部事实。

上述 100% 只表示系统内部引用完整性和规则执行完整性，不表示：

- 报告事实在客观世界中绝对正确；
- 搜索覆盖了互联网上的全部相关信息；
- 来源本身永远不会包含错误；
- 模型能够识别报告中的全部隐含事实；
- 语义 Judge 永远不会发生误判；
- 系统可以实现笼统意义上的“零幻觉”。

语义支持度、事实分类、来源等级分类、研究问题覆盖度和报告可用性应在固定评测集上统计，并同时关注误报和漏报。低于语义置信阈值或不同校验结果冲突时进入 `NEEDS_REVIEW`，不能用未经验证的“100% 准确率”作为项目宣传。

数值目标采用“先测基线、再定阈值”的方式：先运行具有代表性的真实任务和故障注入用例，记录分布，再根据结果制定可达到但有区分度的验收阈值。样本规模、抽样方式、人工标注规则和置信区间必须随评测结果一同说明。

### 12.5 第一版评测集规模

第一版使用 12 个仅依赖公网信息的调研任务：

- 3 个客户背景任务；
- 3 个行业趋势任务；
- 3 个竞品对照任务；
- 3 个完整售前调研任务。

端到端产品验收首先选择一个公开资料较丰富的制造业企业，模拟“第一次技术交流，探索企业知识检索与内部智能问答场景”。该样例不得预设企业已经立项、存在预算或确认需求，只能依据公网 Evidence 形成背景判断、需求假设和待验证问题。

制造业样例只是第一版验收夹具，不是产品行业边界。产品仍面向售前工程师服务的广泛企业客户；行业差异通过 Scenario Profile、条件模块和覆盖多种企业与任务类型的评测集处理，不为每个行业复制一套独立 Agent 流程。

#### 12.5.1 首个端到端验收样例

首个验收对象采用海尔智家。选择理由仅是其官方投资者关系页面和年度报告等公开网页、PDF 适合验证多类型公网摄取，不代表海尔智家真实存在本样例模拟的客户需求。样例运行时仍须重新发现和核对截至运行日期可用的最新来源，不能把预置链接当作永久有效或最新事实。

Research Brief：

```text
research_target     海尔智家
scenario            模拟首次客户技术交流
meeting_topic       探索企业知识检索与内部智能问答场景
known_context       纯模拟商机；没有内部资料，不预设已立项、预算或确认需求
research_goal       形成可核验的客户背景、需求假设、替代方案、异议准备和会议验证问题
source_scope        仅公开网页和公开 PDF
conditional_modules A / B / C / D / E / F 全部启用
time_budget         30 分钟
outputs             同一 ResearchReport 渲染的浏览器 HTML 与 Markdown
```

该样例的产品验收标准：

1. 所有外部事实均能追溯到 Evidence 和 Source；
2. 模拟会议背景不得写成海尔智家的真实需求；
3. 事实、推断和建议明确区分；
4. 高影响事实满足来源等级、交叉验证与时效规则；
5. 证据不足或冲突时正确降级为 Research Gap、`PARTIAL` 或 `NEEDS_REVIEW`；
6. 单个网页或 PDF 失败不能导致整个流程崩溃；
7. 执行摘要中的判断全部能够跳转到正文 Claim；
8. HTML 与 Markdown 中的 Claim、引用、报告版本和状态保持一致；
9. 人工审阅和针对具体 Claim 或 Gap 的局部补充调研可以形成可追踪的 `v2`；
10. 人工抽查 5～10 个高影响事实，评估 Evidence 是否在语义上真正支持 Claim。

其中第 1、2、3、7、8 条属于系统可确定性控制的结构验收项，目标为 100%；第 4、5、6、9、10 条需要通过真实运行、故障注入和人工语义评审验证，具体量化阈值在完成基线后确定。

为了控制个人项目的标注和维护成本，不为每个任务编写整份黄金报告。每个任务只人工标注 5～10 个高影响事实、推荐来源、已知冲突和必要的时间边界，用于评测来源选择、Evidence 定位、Claim 支持关系及报告引用。

任务集需要同时包含：

- 资料充足、容易形成结论的正常任务；
- 一级来源缺失、需要二级来源交叉验证的任务；
- 存在旧数据、来源冲突或同稿转载的任务；
- 模拟搜索超时、网页不可访问和解析失败的故障注入任务。

固定任务集用于版本回归；另保留少量未参与 Prompt 和规则调试的隐藏任务，降低针对固定样本过拟合的风险。

### 12.6 效率指标

效率只在报告通过 P0 可信度硬门槛后进行比较。生成速度更快但包含无效引用或未经验证事实的运行，不计为有效的效率提升。

第一版采用以下效率指标：

1. **人工主动投入时间（主要指标）**：用户填写和确认 Brief、处理待裁决问题、审阅报告以及人工修正错误实际投入的时间；不包含 Agent 在后台自动搜索、抓取、重试和生成时用户可以处理其他工作的时间；
2. **端到端运行时间（次要指标）**：从创建研究任务到进入最终状态的总时间；
3. **首份可用报告时间（辅助指标）**：从创建任务到首次产生通过可信度硬门槛的 `COMPLETED` 或可信 `PARTIAL` 报告的时间，未经校验的草稿不计算在内；
4. **运行成本（约束指标）**：输入及输出 Token、模型调用次数、搜索次数、抓取次数、PDF 解析次数和补充研究轮数；Provider 能提供可靠价格时再换算为金额。

12 个评测任务至少记录：

```text
task_id
运行终态
人工填写和确认 Brief 的时间
人工处理待裁决问题的时间
人工核验报告的时间
端到端运行时间
首份可用报告时间
输入和输出 Token
模型调用次数
搜索、抓取和解析次数
```

个人项目阶段允许使用计时器人工记录主动投入时间，不追求不现实的秒级精度。汇总时优先使用中位数，并同时保留异常任务和失败原因，避免少量网络异常扭曲平均值。

第一版主场景中，用户可接受从提交任务到获得首份可信可用报告的等待时间为 30 分钟以内。当前将 30 分钟作为产品时间预算和评测观察窗口，不在完成基线测试前宣传为所有任务都能达到的 SLA。

“首份可信可用报告”可以是 `COMPLETED`，也可以是已经通过可信度硬门槛并明确披露未完成问题的 `PARTIAL`；未经验证的草稿不计入。评测需要记录每个任务能否在 30 分钟内产生首份可用报告，以及超时原因。涉及大体积 PDF、OCR、动态网页、Provider 限流或来源冲突的任务可能超出该窗口，系统不能为了按时完成而放宽可信度规则。

达到 30 分钟后默认停止扩展搜索并优先完成可信的 `PARTIAL` 报告，不继续无限后台运行。用户可以在审阅后针对具体 Gap 显式续跑。

## 14. 当前已确认的设计决策

- 第一版产品输出以可追溯的结构化调研报告为核心；
- 后续可以扩展为包含方案、汇报提纲和风险清单的完整售前工作包；
- 竞品对照与异议应答是报告中的重要模块；
- 第一版核心用户是售前工程师本人；
- 第一版唯一主场景是为陌生客户的首次客户交流准备可信调研底稿；客户、行业和竞品研究首先作为该场景的支撑能力；
- 报告主要供售前工程师在会前完整阅读和核验，第一版不建设会议中的实时 Copilot；
- 第一版以浏览器 HTML 为主要阅读与审阅界面，以 Markdown 为正式导出格式；两者从同一结构化 ResearchReport 渲染；
- 第一版 HTML 只提供结构化审阅能力，不建设全文富文本编辑器；自由改写通过 Markdown 完成；
- 第一版 HTML 审阅闭环包括查看证据与来源、接受/待核实/驳回 Claim、添加批注、按 Claim 或信息缺口发起补充调研，以及导出当前版本 Markdown；审阅动作必须绑定报告版本和具体对象；
- 第一版浏览器产品固定为新建调研、运行详情、报告审阅和历史记录四个核心视图，不建设独立仪表盘或管理后台；
- 执行摘要固定为一页以内，包含整体调研结论、3～5 条关键发现、售前影响、主要风险与信息缺口、3～5 个优先验证问题和可信状态；摘要只能引用已有 Claim，不得生成新的未校验判断；
- 发现卡片固定展示 Claim 标识与陈述、类型、影响等级、支持和时效状态、证据概况、售前含义、限制与审阅操作；默认折叠证据原文和技术定位，但不得隐藏证据状态；
- HTML 原型中的简短报告不是正式篇幅要求；真实报告按问题覆盖和有效证据自适应展开，不设固定字数，也不允许用无证据内容填充篇幅；
- 竞品和异议准备统一采用“替代方案卡片”，覆盖直接竞品、自建、现有系统、人工流程和不采购；优势、限制、异议与回应逻辑均需保留适用条件和 Claim/Evidence 追溯关系；
- 补充调研在同一 `run_id` 下按目标进行局部增量研究，形成新的不可变报告版本；保留旧版本与审阅记录，并重新校验受新证据影响的事实、推断和建议；
- Claim 未发生实质变化时可继承并标注上一版本的人工审阅状态；内容、关键证据或支持状态变化时，接受或驳回状态均失效并转为待核实；
- 被用户驳回的 Claim 不进入正式报告正文，依赖它的推断和建议随之失效，但 Claim、证据和驳回原因保留在本地审计历史中；待核实项可以保留，但不得表述为已确认事实；
- 系统运行终态和人工审阅进度分开记录；只有全部高影响 Claim 都被接受或驳回后，报告版本才是 `REVIEWED`；未完成审阅时允许导出，但必须显示未审阅或审阅中状态；
- 第一版只公开首次客户交流主入口，底层通过 Scenario Profile 保留客户、行业和竞品等公网调研场景的扩展能力；
- 每次调研作为自包含本地运行包保存，默认不自动云同步并保留到用户主动按 `run_id` 删除；外部调用只发送完成步骤所需的最少信息；
- 销售提供的客户背景、已知需求和当前判断保存为独立 UserContext，可指导研究但不自动构成 Evidence；敏感内容不得原样进入外部搜索或不必要的第三方工具；
- 第一版只使用公网资料；
- 不继续聊天和 AIOps 功能；
- 先本地个人使用，架构上保留服务化边界，暂不建设多人系统；
- 新项目使用独立 Python LangGraph 后端；
- Codex Skill 是可选入口及基线，不是核心运行宿主；
- 项目 A 提供通用能力，PiAgent 框架耦合代码不迁移；
- LangGraph 负责主编排，LangChain 负责模型、工具和标准 Agent 抽象；
- 文档摄取采用分层候选方案：MinerU 主解析 PDF、PyMuPDF 校验和降级；HTTPX 与 Trafilatura 静态网页优先、Playwright 动态降级；具体 Backend 和硬件方案后续通过样本测试确定；
- 采用单个顶层图、可复用研究子图和确定性领域服务；
- 第一版不刻意设计多 Agent；
- Brief 确认和最终报告审阅是两个主要人工介入点；
- Research Brief 只要求用户提供调研对象、使用场景和重点关注三个最小必填项，其余字段由 Agent 提议并在正式研究前统一确认；
- 报告采用必需头部、六个固定核心章节和六个条件模块；条件模块按调研场景默认加载并可在 Brief 阶段调整；
- 报告采用四层阅读体验：一页决策摘要、行动准备、分析细节和证据审计；整份报告不设置固定字数；
- 关键发现使用可解释的证据状态，不向用户展示缺乏校准依据的 0～100 模型置信度分数；
- 采用双层 Lineage：外部事实追溯到 Evidence 和 Source，推断与建议追溯到上游 Claim；
- 用户在第一版 HTML 中进行结构化审阅，不直接编辑事实正文；导出 Markdown 后可以自由修改，但外部修改不属于系统内已验证版本，也不能自动保留原验证状态；
- `PARTIAL` 和 `NEEDS_REVIEW` 允许带明确状态和风险标识导出，但不能伪装为已经验证完成的报告；
- Agent 根据 Research Question 覆盖度、查询新颖性、预期信息增益和预算决定是否停止搜索，不由模型随意终止，也不只依赖固定搜索次数；
- 成功目标以可信度为硬门槛，效率为第二目标；
- 所有外部可验证事实必须具有有效证据，不能只覆盖核心结论；
- 接受三级来源分级策略；高影响事实优先使用一级来源，一级来源缺失时至少需要两个相互独立的二级来源；
- 高影响事实范围包括客户经营与战略、市场数据、法规、竞品能力及价格，以及用于售前判断或可能在客户交流中直接引用的关键事实；
- 接受按事实类型区分的信息时效规则；报告必须显示 `as_of_date`，过期或日期未知的信息需要降级并明确标识；
- 运行终态分为 `COMPLETED`、`PARTIAL`、`NEEDS_REVIEW` 和 `FAILED`，其中 `PARTIAL` 必须保持“不完整但可信”；
- 100% 硬门槛只用于系统可确定性控制的结构不变量；模型语义质量和研究完整性使用真实样本评测，不承诺不可验证的绝对准确或零幻觉；
- 第一版评测集包含 12 个公网任务，每个任务只标注 5～10 个高影响事实、推荐来源和已知冲突，不制作成本过高的整份黄金报告；
- 端到端产品验收先使用一个公开制造业企业及“首次交流探索企业知识检索与内部智能问答”的模拟目标；这只是验收夹具，不把产品限制为制造业专用工具，也不得把模拟会议背景写成该企业的真实需求；
- 首个端到端验收对象确定为海尔智家，启用 A～F 条件模块并按十条结构、可信、恢复、双格式一致性和增量版本标准验收；预置官方链接只作为来源发现种子，运行时仍须重新核对时效；
- 效率以减少售前工程师主动调研和核验时间为主要指标，同时记录端到端时间、首份可用报告时间和运行成本；效率比较仅针对通过可信度硬门槛的结果；
- 第一版以 30 分钟作为首份可信可用报告的用户可接受等待上限和评测窗口；在基线完成前不将其宣传为所有任务均能达到的 SLA；
- 到达 30 分钟时间盒后停止扩展搜索，优先交付可信 `PARTIAL`；后续研究只能由用户针对具体 Research Gap 显式触发；
- 局部工具或来源失败先有限重试和降级，不阻断无依赖的研究分支；用户可以重试具体失败项、跳过来源或提前生成可信 `PARTIAL`，失败影响必须可见并保留审计记录；
- 本阶段只调研和设计，不实现代码。
- 第一版产品需求已于 2026-09-10 冻结；新增用户、场景或输出必须作为显式需求变更处理。

### 15.3 有真实需求后再确认

- Word、PDF 和含审阅排除项的审计版导出；
- 多人共享、权限、租户隔离、并发和集中部署；
- 内部资料、登录态网页和企业知识库接入；
- 未来服务化需要满足的具体共享场景。
